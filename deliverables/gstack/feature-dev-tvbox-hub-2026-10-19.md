## 4.5 A6 反序列化模拟：`zijian.json` 不会有整包加载失败

工具：`scripts/catvod_check.py`。判定依据不是推测，而是真实客户端源码
（`FongMi/TV` 的 `com.fongmi.android.tv.bean.Site`）。

**两条关键事实，此前都判断错了：**

1. `Site.ext` 声明为 `String`，但挂了 `@JsonAdapter(ExtAdapter.class)`，其实现是
   "标量取值、对象/数组取 `json.toString()`"。**所以 `ext` 写对象是完全合法的**，
   会被序列化成 JSON 字符串传给爬虫。主配置里有 10 个、扩展配置里有 94 个这样的站点，
   它们不是问题。
2. `Site.objectFrom()` 整段包在 `try/catch` 里，异常时返回空站点再被 `isEmpty()` 过滤。
   **单个站点写坏了，只会让那一个站消失，不会连累整包。**

结论（主配置 142 站 / 扩展配置 517 站，两份都跑了）：

| 级别 | 主配置 | 扩展配置 |
|---|---|---|
| BLOCKING（整包加载失败） | **0** | **0** |
| SITE（只死单站） | 0 | 0 |
| spider md5 | 声明与实测一致 ✓ | 同 |

因此真正会给用户造成"获取配置失败"的只剩三类：BOM、JSON 语法错、`spider` 取不到或 md5 不符。
这三类当前都不存在。

> 补充：`spider` 用的是相对路径 `./9c8e4-...png`，客户端按**配置文件的 URL** 解析。
> 只要 `zijian.json` 和这个 png 在同一目录（仓库根目录），从 raw / jsDelivr / 代理地址
> 加载都能正确找到。若只把 json 单独复制走、不带 png，则所有 `type:3` 站点会集体失效。

## 4.6 站点页四态口径（505 条，绿 88 / 青 165 / 灰 252 / 红 0）

状态不是"我们测没测过"，而是"**我们对目标知道多少**"。而两类站的目标不是一回事：

- **type1 的目标就是整份配置**。要的是可解析的 JSON，拿不到就等于一无所知。
- **type3 的目标是 `ext` 里的那个地址**。只要拿回任何 HTTP 响应就说明主机活着，
  即使 403、证书异常、返回的不是 JSON——很多 ext 本来就是 `.txt` 域名列表。

按这条拆出来的分布（已用真实数据逐条核算，合计 505）：

| 状态 | 条数 | 构成 | 含义 |
|---|---|---|---|
| 🟢 可用 | **88** | A 档 type1 `confirmed` | 服务端实测拿到真实数据 |
| 🔵 可达 | **165** | B 档 type3 有 `probe_url` | 主机活着，但能否出片未知 |
| ⚪ 未测 | **252** | Y 档 44 + type3 无可探地址 208 | 加密 ext（193）/ 自包含（15）/ 配置级不确定（44）|
| 🔴 失效 | **0** | — | 确认失效的已排除在列表外 |

**红 0 是刻意的。** 探测脚本把 403、TLS 异常、响应截断一律归为 `uncertain` 而不是
`dead`，连不上的才判死并排除——误判"死"的代价远大于漏判"活"。

配套修掉的一个缺陷：原逻辑 `if(!s.probe_url) return 'untestable'` 会一刀切，
而 132 个 type1 站点的 `probe_url` 全是 null（它们的探测目标就是 `api` 本身，
结果存在 `probe_status` 里），导致 **88 个已验证站点被显示成"没测过"**。

**另一个已修的问题：CTA 指错配置。** `includedIn` 是 main 131 / full 374，
即 **374 条站（74%）只在 `zijian-full.json` 里**。原先全部卡片的复制按钮都复制
`zijian.json`，用户粘进 TVBox 后找不到这个站。现按 `includedIn` 分支：main →
「复制主配置」，full → 「复制扩展配置」+ 明示"主配置里没有"。

## 6. ⚠️ 已知局限

### 导入 TVBox 后，最可能先撞上的三件事

按发生概率排序，都是"能用但不完美"，不是"打不开"：

1. **部分站点点进去一直转圈或提示无内容**——主要是 4 个依赖 `./lib/drpy2.min.js` 的
   drpy_js 站点。我实测过那个文件：它现在返回的是一个 HTML 跳转页（指向 gh-proxy），
   不是 JS，所以 TVBox 解析必然失败。这是存量问题，你原来的配置里就有。
2. **搜索能出结果但点了播不了**——`type:3` 的第三方站点，静态只能确认"爬虫类在
   spider 里存在"，确认不了"它对接的目标站还活着"。这类站失效是常态，不是故障。
3. **`米搜`、`csp_PanSearch` 换设备后无效**——它们的 `ext` 指向 `127.0.0.1:9978`，
   也就是 TVBox 自己在手机上起的本地服务。在手机上能用，在模拟器/盒子/网页上不能用。

真正会让"整包打不开"的那一类，A6 已经排除了（见 4.5）。

- **浏览器探测不等于能播**。HTTPS 页面探测 HTTP 目标会被浏览器直接拦截（标「未测」），第三方接口基本不发 CORS 头（标「可达」）。页面显示的是"接入层状态"，不是"能不能看"。
- **扩展配置的 175 条加密源无法预验证**，只能真机试。首次加载慢是正常的。
- **`csp_*` 站点能否播放，还取决于类内部逻辑与目标站点是否匹配**，静态只能确认"类存在"，不能确认"能出片"。
- **未做真机验证**。所有结论基于文件级校验与 HTTP 实测，最终以你的 TVBox 客户端为准。
