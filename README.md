## 接口地址

| 版本 | 地址 | 站点数 | 说明 |
| --- | --- | --- | --- |
| **主配置** | `https://raw.githubusercontent.com/Inliang/tvbox/main/zijian.json` | 142 | 日常使用，只收已验证/自包含的源 |
| 扩展配置 | `https://raw.githubusercontent.com/Inliang/tvbox/main/zijian-full.json` | 517 | 想"全都要"时用 |

> 主配置在原有 51 个站点基础上，从公开接口里筛出 **91 个可迁移的站点源**（type1 采集站 + 自包含 spider 源）。
> 扩展配置额外收 **375** 个站点源（517 − 142），按"可探 → 加密 → 测不准"分三段排在末尾；
> 其中 `csp_*` + ext 指向公网地址的参数化源约 140 个。
>
> ⚠️ 扩展版首次加载明显慢于主配置（内含 175 个加密源，客户端需解密后才能初始化），日常建议使用主配置。

### 站点页的四个状态，怎么读

| 状态 | 含义 | 你用不用它 |
| --- | --- | --- |
| 🟢 可用 | 服务端实测拿到可解析配置 | 直接用 |
| 🔵 可达 | 地址有响应，但拿不到确定结论 | 值得点开试 |
| ⚪ 无法预验证 / 已测无结论 | 加密源、自包含源、或探测没定论 | 只能用起来才知道 |
| 🔴 失效 | 404 / 连接被拒 / DNS 失败 | 已从列表排除 |

页面**有意不做"确认失效"的展示**：连不上的才判死，403、证书异常、响应截断、超时、
镜像站点响应——一律归入灰色。**误判一个站"死"的代价，远大于漏判它"活"**，
因为用户看到红色就再也不会点它了。

正因如此，站点页永远不会出现红叉。你在页面顶部看到的数字会比 517 小一些
（灰色里含大量无法预验证的加密源），这不是缺陷，是"我们不知道"和"它坏了"被严格分开了。

## 接口地址库（网页版）

`docs/index.html` 是一个单文件静态页面，收录 **39 个公开配置接口 / 517 个站点源**，可以搜索、按状态筛选、一键复制地址。

本地打开：直接双击 `docs/index.html`（数据已内联，无需服务器）。
部署到 GitHub Pages：Settings → Pages → Source 选 `main` 分支 `/docs` 目录。

页面里的「状态」含义（**浏览器探测的局限，务必先读**）：

| 状态 | 判定方式 | 能说明什么 |
| --- | --- | --- |
| ● 可用 | 跨域成功且返回了含 sites 的 JSON | 内容可信 |
| ◆ 可达 | 匿名请求有响应（拿不到内容） | 只能说明域名活着 |
| ○ 未测 | 没探测 / HTTPS 页面请求 HTTP 地址被浏览器拦截 | 无法判断 |
| ✕ 失效 | 明确 4xx/5xx 或超时 | 大概率挂了 |

浏览器探测只能证明"接入层有响应"，**不能证明能搜到片**。点「打开」自己验证。

## 数据是怎么筛的

从 2024 个公开接口里解析出站点，按能否在你的配置里跑起来分五档：

| 档 | 条件 | 处置 |
| --- | --- | --- |
| A | `type:1` 且 api 是绝对 URL，实测返回合法 JSON | 合并 |
| B | `type:3` + 参数化类 + ext 含公网 URL | 合并进扩展配置 |
| C | `type:3` + 类存在且无 ext（自包含） | 合并 |
| D | ext 依赖 `./lib/` 或 `127.0.0.1` | 拒绝（换设备即失效） |
| E | 类名不在 spider 里 / api 是相对路径 / 非站点类 | 拒绝（必然失效） |

判定依据是本仓库 `9c8e4-b797010b-….png`（实际是 dex 格式的 spider）里的 **42 个类**，
其中 `Init`/`Proxy`/`Push`/`JSDemo`/`Market` 不是站点类，可用站点类 **37 个**。

> 有个容易被忽略的事实：公开接口里有 **869 个站点引用了不存在的类**。
> 它们不是"后来失效了"，是从来就没能跑起来——把别人的 `csp_XXX` 抄进自己的配置，只要你的 spider 里没这个类，
> 这个站就永远转圈，而且 TVBox 不会报错。
>
> E 档共 1456 条，构成如下（不要把这 1456 全当成"类不存在"）：
>
> | 原因 | 条数 |
> | --- | --- |
> | `class_missing` 类名不在 dex 里 | 869 |
> | `relpath_api` api 是相对路径 | 247 |
> | `remote_js` api 指向远程 js | 175 |
> | `api_not_class` 既非 `csp_` 类名也非地址 | 120 |
> | `type_unsupported` type 为 0/4 | 34 |
> | `non_site_class` 推送/代理/市场类 | 11 |

## 维护脚本

```bash
python scripts/extract.py --probe   # 拆解候选配置，五档分类 + 实测
python scripts/merge.py --dry-run   # 试算合并计划，不写文件
python scripts/merge.py             # 合并（自动备份到 data/backup/ + 校验门禁）
python scripts/build.py             # 重新生成页面数据并内联进 index.html
python scripts/validate.py          # 单独校验配置合法性
python scripts/catvod_check.py      # 模拟客户端反序列化，查整包加载失败的风险
```

`merge.py` 的纪律：只重建 `sites` 数组，其余顶层字段原样拷贝；覆盖前备份；校验不通过不写盘。

`catvod_check.py` 区分「整包加载失败」和「只死单站」两类问题。按 `FongMi/TV` 的
`com.fongmi.android.tv.bean.Site` 源码：`ext` 挂了 `@JsonAdapter(ExtAdapter.class)`，
**写成对象或数组都是合法的**（会被序列化成 JSON 字符串）；且 `Site.objectFrom()` 整段
包在 `try/catch` 里，单个站点解析失败只会返回空站点被过滤，**不连累整包**。所以真正
会让用户看到「获取配置失败」的只有三类：文件带 BOM、JSON 语法错、`spider` 取不到或
md5 不符。

> `docs/data/*.json` 和 `docs/index.html` 里的内联数据**全部由 `scripts/build.py` 生成，请勿手改**。
> 数据源在 `data/exports/`（采集层产出），构建方向是单向的：`data/exports/` → `build.py` → `docs/`。

## 已知问题（原有配置遗留，未擅自改动）

- `csp_Living`（游戏直播）、`csp_LiteApple`（苹果影视）—— 这两个类不在 spider 里，站点必然转圈
- `lib/drpy2.min.js` 实际是一段跳转 HTML（指向 `gh-proxy.net` 上的远端 drpy2），依赖它的两个 js 源（体育直播、儿童启蒙）实际不可用
- 「米搜」「盘搜」的 ext 指向 `127.0.0.1:9978`，只有本机能用

这些都在 `validate.py` 里被标记为 `[KNOWN]`，不阻塞新站点合并。

### 配置页的"可达"不等于"有问题"

39 个配置里有 30 个判定"可用"。其余 9 个不是"坏了"，而是四种不同情况：

| 情况 | 条数 | 说明 |
| --- | --- | --- |
| 带 `//` 注释（JSONC） | 6 | TVBox 宽容解析能用，我们严格解析判不过 |
| 带 UTF-8 BOM | 1 | 同样只是开头三个字节的问题 |
| 多仓格式（`storeHouse`） | 1 | 合法 JSON，只是结构不是单仓配置 |
| 严格 JSON 解析失败（key 没加引号） | 1 | 我们这一侧读不了；Gson 宽容模式可能接受，客户端行为未验证 |

关键点：**这 9 个配置的站点早就收进来了**（比如 `liucn-m` 贡献 98 条站、`hccx-tvbox` 55 条），
卡片上的"可达"只影响那张卡的标签，不影响站点数据。
TVBox 的 Gson 是宽容解析，这些它照样加载；我们用的是严格 JSON，所以判定为"内容不可解析"。

也就是说：**我们比客户端更严。** 这 9 个配置在 TVBox 里大概率能用，
页面标"可达"只是在说"我们没能按严格标准确认它"。

反过来说，这也正是本仓库自己踩过的坑——`zijian.json` 曾有一行
`"changeable": 1 // 1为可切换`，严格解析器直接拒收，**但 TVBox 一直能加载**。
所以这条差异是真实存在的，不是我们的洁癖：严格标准能提前发现"换个客户端就崩"的隐患，
代价是会把一部分能用的东西标灰。

### 已知的"假死"（探测判据的偏差，未修复）

被排除的 28 条死链里，用"失败耗时"可以把三种情况分开：

| 耗时 | 判读 | 条目 |
| --- | --- | --- |
| < 3s | 对方 UA 层主动 RST —— **站其实是活的**，换指纹立刻 200 | 4 |
| > 10s | 通道劣化（TLS 握手 + 读响应超预算），换指纹无用 —— 证据不足 | 4 |
| ~3–10s + 4xx/5xx | 真失效 | 16 |
| 请求未发出 | 路径里的中文没做 URL 编码，本地就抛异常，却被记了"失效" | 4 |

也就是说**有 4 条被判死的站点，HTTP 其实是有响应的**——但这不等于它们能用：
双 UA 复探显示，这 4 个域名返回的是同一个 `<title>Redirecting...</title>` 的 JS 跳转页，
即域名已被跳转接管。所以修掉判据之后，它们的落点是 **2 条从 D 档移到 B 档、2 条移到 Y 档**，
而 B 档语义本就是"无法验证"、Y 档是"保守收进 full 末尾"——**可用站点一条都不会增加**。

v2 要做的是把判据从"抛没抛异常"改成"失败耗时 + 细分错误类型"：
快速失败（＜3s 的 RST/403/429）换浏览器 UA 重试，慢失败（＞3s）同 UA 隔 1s 重试，
并把含中文路径的 URL 先做百分号编码（否则请求根本没发出就被记成"失效"）。
这条在当前版本没有修，因为修复要重跑整个候选层，而当前结论已经冻结。

### 更新后如果地址打不开，先等几分钟

`raw.githubusercontent.com` 和 `cdn.jsdelivr.net` 都有缓存：raw 约 5 分钟，
**jsdelivr 对 `@main` 的缓存可以长达 12 小时**。刚 push 完立刻在 TVBox 里加载，
可能仍读到旧文件（旧那份第 103 行带 `//` 注释，会被严格解析拒绝）。

确认办法：`https://api.github.com/repos/Inliang/tvbox/contents/zijian.json?ref=main`
这个接口直读仓库、不走 CDN。它 OK 就说明仓库是对的，等缓存即可。
jsdelivr 可以主动刷：`https://purge.jsdelivr.net/gh/Inliang/tvbox@main/zijian.json`。
